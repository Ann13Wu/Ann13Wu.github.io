## 一个朴素的问题

假设我要传输一段文字：`ABRACADABRA`。

最省事的办法是每个字符固定用 5 bit（26 个字母至少 5 bit），11 个字符就是 55 bit。但 `A` 出现了 5 次，`B` 2 次，`R` 2 次，`C` 1 次，`D` 1 次——**让出现多的字符用短码，出现少的用长码**，显然更省。

这就是哈夫曼编码的全部动机。

## 建树：每次挑最轻的两个

算法只有一句话：**反复取出权重最小的两个节点，合并成一个新节点，权重相加，放回池子。**

以 `ABRACADABRA` 为例：

```text
初始森林（按权重）:
  C:1  D:1  B:2  R:2  A:5

第1步 合并 C(1) + D(1) = 2
  → 森林: [CD]:2  B:2  R:2  A:5

第2步 合并 [CD](2) + B(2) = 4
  → 森林: [CDB]:4  R:2  A:5

第3步 合并 R(2) + [CDB](4) = 6
  → 森林: [RCDB]:6  A:5

第4步 合并 A(5) + [RCDB](6) = 11
  → 根节点，完成
```

画成树大概是：

```text
              (11)
            ╱      ║
          A:5      (6)
                 ╱   ║
              R:2    (4)
                    ╱  ║
                 B:2   (2)
                      ╱  ║
                    C:1  D:1
```

（左分支记 0，右分支记 1）

于是得到编码：

| 字符 | 频次 | 编码 | 长度 |
| --- | --- | --- | --- |
| A | 5 | `0` | 1 |
| R | 2 | `100` | 3 |
| B | 2 | `101` | 3 |
| C | 1 | `1100` | 4 |
| D | 1 | `1101` | 4 |

总长度：`5×1 + 2×3 + 2×3 + 1×4 + 1×4 = 25 bit`，比固定编码的 55 bit 省了一半多。

## 实现：优先队列

```cpp
#include <queue>
#include <vector>
#include <string>
using namespace std;

struct Node {
    char ch;
    int freq;
    Node *l, *r;
    Node(char c, int f) : ch(c), freq(f), l(nullptr), r(nullptr) {}
};

struct Cmp {
    bool operator()(Node* a, Node* b) const {
        return a->freq > b->freq;   // 小顶堆
    }
};

Node* build(const vector<pair<char,int>>& freq) {
    priority_queue<Node*, vector<Node*>, Cmp> pq;
    for (auto& [c, f] : freq)
        pq.push(new Node(c, f));

    while (pq.size() > 1) {
        Node* a = pq.top(); pq.pop();
        Node* b = pq.top(); pq.pop();
        Node* p = new Node('\0', a->freq + b->freq);
        p->l = a; p->r = b;         // 约定：小权重在左
        pq.push(p);
    }
    return pq.empty() ? nullptr : pq.top();
}
```

关键点：

- `priority_queue` 默认是大顶堆，比较器要**反着写**（`>` 表示小顶堆）
- 合并时可以自由决定左右顺序，但**编码端和解码端必须约定一致**，否则解出来全是乱码
- 只有 1 种字符时需要特判，给它分配编码 `0`

## 一个反直觉的结论

**频率最高的字符，不一定拿到最短的编码。**

听起来很怪——哈夫曼不就是让高频字符变短吗？

问题在于「最短」是**相对**的。考虑四个字符 `A:3, B:3, C:2, D:2`：

```text
第1步  C(2) + D(2) = 4   →  森林: A:3  B:3  [CD]:4
第2步  A(3) + B(3) = 6   →  森林: [CD]:4  [AB]:6
第3步  4 + 6 = 10        →  根
```

| 字符 | 频次 | 编码 | 长度 |
| --- | --- | --- | --- |
| A | 3 | `100` | 3 |
| B | 3 | `101` | 3 |
| C | 2 | `00` | 2 |
| D | 2 | `01` | 2 |

**频次最高的 A 用了 3 bit，频次最低的 C 只用了 2 bit。**

原因：哈夫曼保证的是**带权路径总长最小**（`Σ freq × depth`），不是「频率越高编码越短」。当权重分布比较均匀时，合并顺序会产生「先合并的被压到更深层」的效果，于是出现这种反转。

> 优化的是总和，不是个体。
> 这条规律好像不只适用于算法。

## 复杂度与适用边界

| 项目 | 值 |
| --- | --- |
| 建树 | O(n log n)（用优先队列） |
| 编码 | O(n) |
| 空间 | O(n) |

它有两个实际限制：

1. **需要两遍扫描**——第一遍统计频率，第二遍才编码。流式数据不适用，得改用自适应哈夫曼。
2. **有码长下界**——每个字符至少 1 bit。当数据熵很低（比如一亿个 `A`）时，哈夫曼只能压到 1 bit/字符，而算术编码能压到接近 0。

实际压缩工具（zlib、gzip）用的是哈夫曼 + LZ77 的组合：先用 LZ77 消除重复串，再用哈夫曼给结果做熵编码。

## 写在最后

我第一次学哈夫曼的时候，觉得它就是个贪心的小技巧。后来做 CTF 遇到 zlib 的 dynamic Huffman 题，得手算码表去还原压缩数据，才发现：**所谓「最优」从来不是某个字符的最优，而是整体的最优。**

给出现多的东西更短的路——但这条路的长度，得由所有字符一起决定。
